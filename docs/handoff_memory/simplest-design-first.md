緊急パッチの溜まり対策で、「一度当てればいい・溜まらなければいい」だけの話に、廃止・レシピ・並べる仕組み・期限の必須化・冪等の決まりまで積み上げ、ユーザーに「なぜこれしきのことをそこまで捏ねたのか、不安」と言われた。答えは「同じ名前のファイルで上書き」だけで、コード変更もほぼ不要だった。

**Why:** 失敗を二度続けたあとで身構え、要件から考えずに思いつく対策を全部載せた。過剰修正は、それ自体がクレジットとユーザーの信頼を減らす。
**How to apply:** 提案の前に要件を一行で言い直し、それを満たす最小の形を出す。追加の仕組みは、それが無いと壊れる具体的な手順を一つ挙げられるときだけ。ユーザーの指示の言い回しは、字面ではなく要件として読む（「極力使うな」を「廃止」と取らない）。[[kurashi-deliver-to-prod]]
