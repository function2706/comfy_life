# 作業の進め方（セッション向け）

kurashi で作業するセッションは、まずこの 1 枚を読む。**クレジットの節約が最優先**（遅くてよい）。
セッションは作業 1 つごとに新しく立て、長く使い回さない。会話は次のセッションに残らないので、決めたこと・分かったことは終わる前に docs に書く。

## 1. 最初のひとことと、やること

| ひとこと | やること |
|---|---|
| `残件 S3`（または `残件 A22`） | [REMAINING.md](REMAINING.md) のそのまとまりを実装する（3〜6 章） |
| `設計 A15` | コードは書かず、設計を REMAINING のその項目に書く（A17 の「設計」の形: 段の切り方・データの形・遡及・当たり所・テストで確かめる点）。終わったら「まとまりの表」の設計の列を「済」に |
| `残件追加: …` | 7 章。REMAINING に足すだけ（実装しない） |
| `不具合: …` | 8 章 |
| `セリフ S3` | 5 章。実装済みの場面に性格別のセリフを足す |
| `全テスト` | 9 章 |

ひとことに無い作業を勝手に広げない。途中で見つけた別件は、直さずに残件へ足す（7 章）。

## 2. 読む範囲（全部は読まない）

| ファイル | 読む所 |
|---|---|
| この WORKFLOW.md | 全部 |
| [REMAINING.md](REMAINING.md) | 冒頭〜「まとまりの表」と、自分の項目だけ（`### A22` などを検索して、その節を行の範囲で読む） |
| [DESIGN.md](DESIGN.md) | 1 章（公理）と 2 章（構成）。4〜5 章は触る概念の節だけ。8 章は移行・既定の定義を触るとき。9 章は読まない |
| [CHANGES.md](CHANGES.md) | 「版の決まり」と「次の版」だけ（過去の版は読まない） |
| `README.md`・`static/manual.html` | 読み通さない。触る機能の語で検索し、その節だけ |
| コード | 項目に書いてあるファイル・関数から。無ければ検索で当たりを付ける。大きいファイル（`core/engine.py`・`static/app.js`）は範囲を指定して読む |

サブエージェント（Agent）は使わない。自分で順に進める。

## 3. 設計の決まり（必ず守る）

- **公理**（DESIGN 1 章）: 現実的に・清濁併せ呑む。回数や贈り物で必ず深まる道を作らない。見えないはずのものを見せない。新しい交流や効果は `bonds.realize` を通す。
- **あなた（プレイヤー）の心理の値は作らない**: 不満・我慢などは操作者のもの。動かすのはキャラクターの値と、あなたが実際に払うもの（お金・時間・体力）だけ。表示もしない。
- **遡及を毎回判断する**: 値・判定を変えたら、いまのセーブに遡って効かせるかを決め、項目と報告に「遡及: する（どこまで・一度だけ・二重にしない）/ しない（理由）」を書く。
- **基本の堅さは言われる前に**: 閉じる・開き直す・再起動・二重に開く・途中でやめる、を自分で確かめて穴を塞ぐ。プレイヤーが損をする不具合は、直すだけでなく一度だけの補償も考える。
- **入力中の欄**: 画面は 30 秒ごとに描き直される。プルダウン・時刻・文字の欄・スクロールする欄を足したら、`tools/test_focus_keep.py` に項目を足す。
- LLM は基本使わない（数値と規則で）。
- 項目に「未確認」「着手前に確かめる」とある所は、まずコードで確かめる。項目の前提と実際のコードが食い違っていたら、進める前にユーザーに伝える。

## 4. 実装 → テスト → 記録 → コミット

1. 実装する。
2. **関連テストだけ**流す: 足したテスト、触ったモジュール名の `tools/test_*.py`。`engine` / `chat` / `presence` を触ったら `test_chat`・`test_msgreply`・`test_presence`・`test_manners` も。全テストは流さない。
3. テストは整合性を重視して足す（状態 × 行動の総当たり、「画面で押せる = 本当にできる」の突き合わせ）。数は気にしない。
4. 使い方が変わったら `README.md` と `static/manual.html` の該当の節を直す。構成・概念が変わったら DESIGN の該当の節も。
5. `CHANGES.md` の「次の版」に足す（区分と beta）。`REMAINING.md` から片付いた項目を消し、「まとまりの表」も直す。一部だけ済んだなら、残りを項目に書き直す。
6. コミット: `git status --short` で入れ忘れ・自分のものでない変更が無いか確かめ、ファイルを列挙して `git add`。メッセージは 1 行目英語（末尾に `(1.7.0beta)` のように版）、2 行目以降は日本語の箇条書き。`Co-Authored-By` は付けない。記録（5.）は同じコミットに入れる。push はユーザーに言われたら。
7. `VERSION` は書き換えない（上げるのは全テストのあとだけ。9 章）。

このPCの 8765 番は別のアプリが使っている。動かして確かめるときは `KURASHI_DATA=<一時フォルダ>` と別のポートで。画像生成は `tools/mock_comfy.py` で代用する。

## 5. セリフ

- 新しい場面（セリフのキー）が要るときは、**共通のセリフだけで実装をコミット**する。キーは `core/keys.py` に登録する。
- 性格別のセリフは実装のセッションでは書かない。行数（場面数 × 性格数）を数え、REMAINING に「セリフ待ち: キーの一覧・行数・場面の説明」の項目を足して終わる。書くのは、ユーザーが了承して立てた別のセッション（`セリフ …`）。
- 書き方: 口癖・決め台詞・お約束の言い回しで性格を出さない。地の口調（タメ口 / 敬語）と、何に反応しどう考えるかで出す。一人称は `{fp}`。書いたあと、目立つ語・語尾・間投詞の出現数を数えて、多ければふつうの言い回しに戻す（目安は数本）。
- 確かめ: `python tools/check_persona.py`・`check_tone`・`test_personas`。
- 報告の本文に、性格ごとに代表的なセリフを数本ずつ引用する（ユーザーが口調を確かめるため。必須）。

## 6. 終わるとき・報告

- 報告は日本語で短く: やったこと / テスト（流したものと結果）/ 遡及 / 残したこと・確かめていないこと / 足した残件。
- 終わらなかったら、どこまで済んだか・次に何をするかを REMAINING の項目に書いてから終える（次のセッションはそれだけを読む）。
- 時間のかかる作業は、区切りごとに一行で進捗を伝える。
- ユーザーへの質問に選択肢の箱を使うときも、説明の本文を先に書く。

## 7. 残件を足す（`残件追加`・作業中に見つけた別件）

- 入れるのは保留・未着手だけ。実機での確認待ちは入れない。
- 修正は F 番、機能追加は A 番（続きの番号）。状態・追加日・重さ・内容。分かっていれば、関わるファイルと関数・関連テスト・決まっていること・着手前にユーザーに聞くこと・遡及・セリフの有無（**着手メモ**）も書く。項目は、それだけ読めば着手できるように書く（「さっきの件」のような、会話が無いと分からない書き方をしない）。
- **まとまりの吟味（足すたびに必ず）**: 「まとまりの表」を見て、新しい項目をどこに入れるか決める。
  - 同じファイル・同じ画面・同じ判定を触る項目は、同じまとまりに入れる（読み込みが 1 回で済む）。
  - 1 つのまとまりは、1 つのセッションで終わる大きさに（目安: 軽 2〜3 個、または中 1 個 + 軽 1 個。重は段ごとに 1 つ）。超えるなら分ける。
  - 設計が要るもの（新しい値・移行・判定の作り直し）は、設計の列を「要」にする。小さな修正・画面だけの変更は「不要」。
  - ほかの項目の前提になる・前提にする関係があれば、順の列に書く。
  - 入れた結果、表のほかのまとまりも組み直したほうがよければ直す。
- コミット: `REMAINING.md` だけを入れる（`Add remaining items …`）。

## 8. 不具合の報告（`不具合`）

- 実運用は別のPC。貼られた経過ログ・`data/server.log`・症状から切り分ける。こちらでは一時フォルダとモックで再現する。
- すぐ直せる（軽）ならこのセッションで直す（4 章）。大きければ、分かった原因と再現の手順を付けて残件に足す（7 章）。

## 9. 全テスト（`全テスト`）

- `tools/test_*.py` を、分野ごとに 3〜4 回に分けて流し、区切りごとに「◯/◯ 本、落ちたもの」を一行で伝える。出力は要約だけ見る（落ちたものだけ詳しく）。
- `test_reuse_dress` と `test_comfy_output` は `python tools/mock_comfy.py --port N` を立てて `--comfy-port N`。
- 落ちたものは直して、そのテストを流し直す。
- 全部通ったら、`VERSION` を上げ、CHANGES の「次の版」を確定の見出し（日付つき）にして、コミット。

## 10. 同時に動かすセッション

- コードを書くセッションは、同時に 1 つだけ（同じ作業フォルダを直接書き換えるので、2 つ動かすと互いの変更がコミットに混ざる）。
- `残件追加` のような docs だけのセッションは並べてよい。`git add` は自分のファイルだけにする。
